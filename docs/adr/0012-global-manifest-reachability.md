# The Global Manifest reaches a project only through its own Manifest, never across a nested repository

A machine ends up running the same few Handles — a GitHub token, a cloud credential — in every project it touches, and declaring each one in every project's `.claudepass.toml` is exactly the repetition a Manifest was supposed to remove. We added a second file, `$CPASS_HOME/global.toml` (the Global Manifest), in the same TOML subset as a project Manifest and carrying no values, declaring the Handles this machine wants everywhere. `cpass add -g` and `cpass global` write it; `cpass local` removes an entry without touching the stored Secret.

Global-ness belongs in a Manifest-shaped file rather than as a flag on `vault.Entry`. The Vault is already machine-global — every Handle in it is available on this machine to any command that asks for it by name — so a boolean there would conflate two different things: where a Secret is *stored* (always the Vault, always this machine) and which projects get it *without being asked* (a scoping decision, exactly what a Manifest already exists to record). Keeping the two separate means a Handle can be stored and later promoted, demoted, or scoped differently per project without touching the Vault at all, and it means the Global Manifest can be read, diffed and reasoned about with the same code (`internal/manifest`) that already reads a project's.

`manifest.Refs` is the single place both `cpass run` and the MCP `run_with_secrets` tool go for "what Handles apply here" when neither gives an explicit list. It layers the Global Manifest as a base and lets the project's own Manifest replace any entry for the same Handle outright — Binding included — because a project's committed contract always outranks the machine's ambient default. `--with handle[:VAR]` layers over both, and an MCP call's own `handles` list replaces the result entirely, even when given as empty: an Agent that asked for nothing gets nothing, never a Global Handle it didn't request.

A Global Handle reaching a directory needs two things true: a project Manifest found from that directory by the ordinary ancestor walk (`manifest.Find`), and no directory between the command's own directory and the Manifest's crossing a nested repository of its own — detected by the presence of a `.git` (`globalReaches` in `internal/manifest/refs.go`). This is the load-bearing part of the design. Without it, `cpass run` would hand the machine's ambient Secrets to an install script inside a dependency cloned into `vendor/` or a scratch checkout under `tmp/` — a tree nobody reviewed and nobody ran `cpass manifest init` for — the moment that tree sat inside an onboarded project. The gate withholds Global Handles the instant the walk crosses that boundary, while the outer project's own explicitly declared Handles still reach the nested directory exactly as they always have: that is the pre-existing meaning of a committed Manifest, and this feature does not touch it. Both ends of the walk are resolved through `filepath.EvalSymlinks` before it starts, because the walk is lexical (`filepath.Dir` is string surgery) while the boundary check is a syscall the kernel resolves through links: without resolving, a symlink at the project root pointing into a nested repository has a lexical parent of the project root itself, and the walk steps straight over the directory holding the `.git` — handing an untrusted tree every Global Handle. Package managers and monorepo tooling create exactly that shape routinely. The named residual: the gate keys off finding a `.git`, so an untrusted tree extracted without one — a tarball, a directory copied rather than cloned — is indistinguishable from an ordinary subdirectory and still receives Global Handles. This is disclosed rather than fixed, because detecting "untrusted" any other way (a prompt, an allowlist) would reintroduce exactly the friction the Global Manifest exists to remove.

We rejected two other gates. An exact-directory-match — Global Handles apply only in the directory the Manifest itself lives in — was tried first and rejected because it breaks the ordinary case a Manifest is for: `cd`-ing into a subdirectory of your own project and running `cpass run` there is the single most common way `cpass run` actually gets invoked, and a gate that punished it would make the Global Manifest useless for anything but repo roots. A reserved Handle prefix (Handles named e.g. `global/*` are always ambient) was also rejected: it conflates a Handle's name with its scope, means renaming a Handle changes its trust boundary by accident, and gives a project's own Manifest no way to shadow a prefixed name the way `Refs` already lets it shadow an ordinary one.

Two asymmetries follow from the Global Manifest being ambient rather than committed. First, resolution: a Global-sourced Handle that cannot be resolved — removed from the Vault, or in CI mode its variable missing from the environment — is skipped with a notice (`skipNotice` in `internal/broker/broker.go`) and the run proceeds; a Handle the project itself declared, or one named in the MCP `handles` list, still hard-fails as it always has. `cpass run --with handle[:VAR]` counts as naming it: `cmdRun`'s merge loop (`internal/cli/runcmd.go`) clears the existing Ref's `FromGlobal` mark along with applying the override, so a Handle typed on the command line hard-fails when it cannot be resolved even though the same Handle would have been skipped had it only arrived ambiently. This mirrors `replaceOrAppend` in `internal/manifest/refs.go`, which clears the same mark when a project Manifest supersedes a Global entry — in both cases, something explicit has taken ownership of the Handle, and explicit things fail loudly. The same asymmetry covers the file itself: a `global.toml` that will not parse costs the run its Global Handles and a notice, while a project's own unparseable Manifest is still fatal. One drifted machine-wide declaration — or one half-written machine-wide file — must not break every project that happens to run on this machine at once, but a project's committed contract is still a contract. Second, collisions: two Handles binding the same environment variable are refused — `cpass: handle collision: <a> and <b> both bind <VAR>`, exit 1, on `cpass run` — only when at least one of them came from the Global Manifest (`checkCollision`). The MCP `run_with_secrets` tool refuses the identical collision as an `isError: true` tool result whose text is the same message with no `cpass: ` prefix and no process exit code: `callRunWithSecrets` (`internal/mcp/tools.go`) returns the broker error as-is, unlike the CLI path which prepends `cpass: ` when printing to stderr. Two Handles a project declares into the same variable itself keep today's silent last-write-wins, unchanged: a project that never opted into the Global Manifest, and never will, must not start failing on a `cpass` version bump it never asked for.

A project opts out durably with `cpass manifest global off` (or `cpass manifest init --no-global`), written as `[options] global = false` in its own committed `.claudepass.toml` — a property of the file everyone reviews, not a setting one developer happens to have locally. `manifest.Load`/`Save` now keep, verbatim, any `[options]` key or whole section this binary does not itself parse, so that line survives a `cpass manifest add` run by any binary at or above this version. The disclosed limit: a `cpass` binary older than this feature does not know to preserve it, and will silently drop it on its next `Save` — an old binary overwriting a Manifest is already capable of losing anything it doesn't parse, and this is one more instance of that, not a new failure mode.

## Consequences

- `docs/SECURITY.md` and `docs/THREATS.md` must describe the Global Manifest, the reachability gate, and the tarball residual in full — this ADR states the decision, those pages state the mechanism.
- A future change to the reachability heuristic (for example, detecting an untrusted tree some way other than `.git`) needs a superseding ADR, not a silent edit to `globalReaches`.
